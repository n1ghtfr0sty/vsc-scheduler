# 2026-07-08

## Bug Fix: All clicks dead in the UI (CSP `script-src-attr`)

- **Symptom:** After the security-hardening changes (commit `427b983`), the app rendered normally but no button or link responded to clicks.
- **Root cause:** Helmet's `contentSecurityPolicy` merges its defaults into custom directives (`useDefaults: true`). The default `script-src-attr 'none'` overrides `script-src` specifically for inline event-handler *attributes*, blocking all 66 `onclick="..."` handlers in `public/js/app.js`, `calendar.js`, and `auth.js`. The custom `scriptSrc: 'unsafe-inline'` never applied to them.
- **Fix:** Added `scriptSrcAttr: ["'unsafe-inline'"]` to the CSP directives in `src/index.js`. No net security change — `script-src` already allowed `'unsafe-inline'`.
- **Verification:** Served CSP header on a test instance now ends with `script-src-attr 'unsafe-inline'`; user confirmed buttons and access work again after restarting the server.
- **Files changed:** `src/index.js` (CSP directives block, ~3 lines).

## Bug Fix: "Invalid CSRF token" on all create/update/delete

- **Symptom:** Adding a new season (and any other state-changing action) failed with "Invalid CSRF token. Please refresh the page and try again."
- **Root cause:** The security-hardening commit (`427b983`) added backend CSRF enforcement (`src/middleware/csrf.js`, mounted globally on `/api/` in `src/index.js`) requiring an `X-CSRF-Token` header on all POST/PUT/DELETE/PATCH for logged-in sessions. The frontend `API.request` (`public/js/api.js`) was never updated to send it — the token was generated server-side but only exposed via `/api/auth/me`, and the frontend never read or forwarded it. Affected every mutation, not just seasons.
- **Fix:**
  - `public/js/api.js`: added `API.csrfToken`, captured from any response containing `csrfToken`, and attached as `X-CSRF-Token` header on non-GET/HEAD/OPTIONS requests.
  - `src/routes/auth.js`: added `csrfToken` to the login and register JSON responses (previously only `/me` returned it) so the token is available immediately after login without a page reload.
- **Verification:** On a test instance (port 3999), login now returns `csrfToken`; POST /api/seasons returns 403 without the header and succeeds with it. Test data cleaned up.
- **Files changed:** `public/js/api.js`, `src/routes/auth.js`.

## Feature: Responsive nav — "More ▾" dropdown + mobile hamburger

- **Why:** 12 nav buttons were cluttering desktop and wrapping into a blob on mobile.
- **Design:** spec at `docs/superpowers/specs/2026-07-08-responsive-nav-design.md`. Desktop shows Dashboard/Schedule/Games + "More ▾" dropdown (only if the role permits overflow links); ≤768px collapses to brand + ☰ with a slide-down panel (all links flat, divider, user + Logout).
- **Implementation:**
  - `public/index.html` — added ☰ toggle button and mobile panel container to `<nav>`.
  - `public/js/auth.js` — nav links defined once in a `NAV_LINKS` data array; `updateUI()` renders trio + dropdown + panel from it (replaced duplicated template strings). Added `toggleMoreMenu`/`toggleMobileNav`/`closeMenus` and one document-level outside-click/Escape listener. User name now escaped via `escapeHtml`.
  - `public/css/style.css` — dropdown/hamburger/panel styles on existing CSS variables; replaced old ≤768px stack-and-wrap navbar rules; both menus get `max-height` + scroll for short screens.
- **Verification:** headless Chrome (puppeteer-core) against a :3999 instance — desktop bar/dropdown, Escape/outside-click close, navigation closes menus + `.active` highlighting, 375px hamburger panel, logout from panel, coach role sees only permitted links (no Events/Users), 640×360 landscape panel scrolls so Logout stays reachable. No CSP/console errors.
- **Also:** added `.claude/skills/verify/SKILL.md` — project recipe for driving the app headlessly (test instance on :3999, login/CSRF pattern, Chrome path, gotchas).

## Feature: Grant All / Clear All permissions on the user permissions panel

- **Why:** GitHub issue #6 — setting 40 checkboxes (10 resources × 4 actions) per user is tedious. Admins want one-click bulk operations.
- **Implementation:** `public/js/app.js`
  - In `renderUsers()`, added an `isAdmin` flag per card and a `bulkActions` row that prepends **Grant All** / **Clear All** buttons to the permissions table only for non-admin users (admins get all permissions by role and have all checkboxes disabled, so the buttons would be misleading).
  - Added `App.grantAllPermissions(userId)` / `App.clearAllPermissions(userId)` — flip every permission checkbox on that user's card, then call the existing `saveUserPermissions()` which already PUTs the full permission set in one call (backend `src/routes/users.js` upserts the full 9-resource row set).
- **Verification:** headless Chrome (puppeteer-core) against a :3999 test instance — admin card has no bulk buttons + 40 disabled checkboxes; non-admin (coach) card has both buttons; Grant All sets 40/40 checkboxes and persists to API (all 36 perms true); Clear All clears 40/40 and persists (0 perms true). No CSP/console errors. Test user permissions restored.
- **Closes:** GitHub issue #6.
